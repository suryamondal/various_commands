\begin{abstract}
\noindent
We describe an opportunistic HTCondor pool assembled from office desktops, in
which every participant's own machine is both a submit client and an execute
node, and in which machines move between two subnets that cannot route to each
other. Nobody logs into a submission host; jobs are submitted from the machine
their owner already works on.

Two findings generalise beyond this deployment.

First, admission control gated on resource \emph{requests} rather than
\emph{measurements} systematically underuses machines, and the gate is not where
policy authors expect it. HTCondor's partitionable-slot \kn{Memory} attribute is
a reservation ledger consulted by the matchmaker \emph{before} any policy
expression is evaluated. On a sixteen-core worker running eight jobs that each
requested 3\,GB and used almost nothing, the slot advertised 2366\,MB free while
24589\,MB was genuinely available, and the machine refused further work with
half its cores idle. Publishing measured headroom from a \kn{STARTD\_CRON} job
overrides that ledger: twelve jobs requesting 3\,GB each then ran concurrently
on a machine whose configured total was 26942\,MB, with no claim refusals and
CPU correctly becoming the binding constraint. HTCondor's documentation, and an
earlier revision of this note, described the attribute as one that could not
safely be overridden. That was asserted rather than tested, and it is wrong.

Second, eleven separate defects encountered during this deployment shared a
single shape: the configuration parsed cleanly, the diagnostic tools reported
correct values, and the feature did nothing. None produced an error, and several
produced a pool that looked healthy by every command an operator would naturally
run. We attribute this to three properties that declarative policy systems
commonly share, and describe the verification discipline that follows from it.

We also report a naming and addressing scheme that lets execute nodes move
between unroutable subnets while carrying no network configuration of their own,
deriving at startup which of the entry node's addresses they can reach.
\end{abstract}
